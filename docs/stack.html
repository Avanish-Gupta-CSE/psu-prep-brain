The three gotchas that will bite you specifically

Gotcha 01
Jakarta, not javax.
Spring Boot 3 uses jakarta.persistence.*. Every tutorial older than 2023 teaches javax.* — which will not compile.
Gotcha 02
No WebSecurityConfigurerAdapter.
Deleted in Spring Security 6. You configure a SecurityFilterChain bean instead.
Gotcha 03
jjwt 0.12 changed its API.
Jwts.parser().verifyWith(key) replaces setSigningKey. Old examples fail to compile.
Rule: if a tutorial is older than 2023, it is teaching a framework that no longer exists. Check the publish date before you read it.

No evenings. No weekends. Everything happens between 10:00 and 18:30.

Total ≈ 4 hours a week, all inside work hours. This is the entire cost of the plan.

The rule that makes it work: never read a file twice the same way. If you re-read a file and understand it "because you've seen it before", you have learned nothing. Close it and rewrite the core method from memory. The diff is the lesson.

06The defence drill

Train the exact thing you're afraid of

The five questions — ask them of every file, in order

1. What is this file for?
One sentence, no jargon.
2. Who calls it, and what does it call?
The neighbours.
3. What breaks if I delete it?
The blast radius.
4. What is the single most important line, and why?
The crux. If you can't answer this, you don't own the file.
5. What would I change if I owned it?
The judgement that separates a junior from an owner.

The reconstruct technique — the AI-dependency cure

1. Open the file. Read it once, slowly.
2. CLOSE IT.
3. In a scratch file, retype the core method from memory.
4. Diff against the original.
5. Study ONLY the diff. That is your actual gap.
6. Next week, repeat. Target: empty diff.
This is the highest-leverage 15 minutes in the entire plan. AI wrote the code; reconstruction is how you take ownership of it. One method per day is enough.

07The no-AI unblock protocol

What to do when you're stuck and there's no assistant

Timebox each step to 5 minutes. Total 20. Then ask a human — asking after 20 minutes of real effort is a sign of competence, not weakness.

Step 1
Read the stack trace from the bottom up
The root cause is the last Caused by, not the first line.
Step 2
Reproduce it in 10 lines
Strip everything away until it breaks in isolation.
Step 3
Grep the codebase for the same pattern
If it works elsewhere, diff the two. Most answers are already in your repo.
Step 4
Read the official docs section
spring.io/docs, docs.oracle.com. Not a blog, not a video.
Step 5
Set a breakpoint
Inspect the actual values. Beginners assume; debuggers don't.
Step 6
Write the question, then ask
Use the script below. Never ask "how do I write X" — ask where an existing example lives.

The structured question script

"I'm looking at X.
 I expected Y because Z.
 What I actually see is W.
 Is my mental model wrong, or is this a known quirk?"

Three effects: it proves you traced it, it gives the helper the exact failure, and it makes you look like an engineer rather than someone asking for code.

Never ask: "How do I write X?" → ask "where is an existing example of X in our codebase?"
Never ask: "Why is this broken?" → attach the trace and your hypothesis.

08Question bank

One per day for the first month

Each is designed to be genuinely useful and to signal seriousness. Question 18 is the most important one in the list.

Architecture
  1. Which module is the most critical path, and why?
  2. What's the one piece of this system nobody wants to touch?
  3. Where is the line between what we build and what the vendor owns?
Process
  1. How does a change get from my laptop to production?
  2. Who signs off, and in what order?
  3. What happens if a release breaks — who rolls it back?
  4. Is there a code review step, or does it go straight to UAT?
Data
  1. Which tables are shared with other departments, and which are ours alone?
  2. Is there a data-retention or masking rule before I query production?
  3. How do I get read-only production access, and what's the approval chain?
Security
  1. Where are secrets stored, and who can read them?
  2. Is there a VAPT cycle, and when is the next one?
  3. What's the audit-trail requirement for the actions my module performs?
Team
  1. What does a good week look like for you?
  2. What's the most common mistake new joiners make here?
  3. Who do I go to for Oracle questions vs Spring questions?
  4. Is there a design doc or architecture diagram anywhere?
Growth — the important ones
  1. What would make you confident I can own a module on my own?
  2. Which part of this codebase would you want rewritten, if you had a month?
  3. What should I read to be useful faster?
Question 18 tells you the actual promotion criteria — and it tells your manager that you are thinking about ownership rather than survival.
